# Архитектура tg-mcp-spy

Проект вырос из простого MCP-сервера в платформу агрегации лент
(Telegram + RSS/RSSHub) с локальным ИИ-агентом и веб-интерфейсом.
Ключевая идея текущей архитектуры — **доменное ядро** (сбор/хранение/темы)
плюс **тонкие адаптеры** (веб-API и MCP), которые не зависят друг от друга.

## Принципы

- **MCP-сервер — корневое ASGI-приложение.** `mcp.streamable_http_app()`
  отдаёт протокол MCP на `/mcp` (проверенный паттерн, без проблем
  с монтированием/переадресацией). Веб-маршруты и статика добавляются
  через `mcp.custom_route`. Всё на одном порту.
- **Логика не живёт в транспортном слое.** Веб-роуты и MCP-инструменты —
  тонкие обёртки, вызывающие слои `db` / `ingest` / `topics`.
- **Конфиг типизирован (pydantic).** Без ручного мёржа dict'ов.
- **Фоновый воркер изолирован.** Планировщик + прогон агента можно поднять
  отдельным контейнером (`tg-spy worker`), чтобы тяжёлый LLM-прогон не
  влиял на отзывчивость UI.

## Слои

```
src/tg_spy/
├─ config.py            # pydantic AppConfig: провайдер, модель, расписание
├─ db/                  # слой данных (SQLite)
│  ├─ connection.py      # подключение, миграции, ротация по лимиту
│  ├─ migrations/        # 0001_init.sql (версионированный DDL)
│  └─ repositories/      # sources / posts / topics (по сущностям)
├─ ingest/              # сбор лент
│  ├─ telegram.py        # парсер t.me/s
│  ├─ rss.py             # парсер RSS/RSSHub
│  └─ refresh.py         # пересборка (исп. web, mcp, scheduler)
├─ topics/              # «Мои темы»
│  ├─ agent.py           # вызов LLM + отбор постов (mode='ai')
│  ├─ engine.py          # «движок»: сбор хронологии по тегам
│  └─ service.py         # оркестрация (CRUD тем, запуск агента)
├─ mcp/                 # адаптер MCP (инструменты/ресурсы/промпты)
├─ api/                 # адаптер веб (Starlette-роуты + статика)
│  └─ web.py
├─ scheduler/           # APScheduler: обновление ленты + запуск агента
├─ web/static/          # фронтенд (ES-модули, без сборки)
└─ cli.py               # tg-spy serve | worker | migrate
```

## Поток данных

1. `ingest.refresh` подтягивает посты из Telegram/RSS → `db` (posts).
2. `scheduler` по расписанию запускает `topics.agent` для каждой активной
   темы; агент просит слабую модель отметить релевантные посты (теги).
3. «Движок» (`topics.engine` / репозиторий) собирает посты с тегом темы в
   хронологию — модель только *размечает*, никакой аналитики.
4. Веб-UI и MCP-инструменты читают темы/посты через тот же доменный слой.

## Чем отличается от предыдущей версии

- Единый процесс, но с явным разделением слоёв (раньше `main.py`/`webui.py`
  мешали транспорт и логику).
- Провайдер ИИ и расписание — в типизированном `AppConfig`.
- Источники/посты/темы — в отдельных репозиториях; схема БД версионируется
  миграциями.
- Планировщик не блокируется: прогоны агента уходят в пул потоков.
- Фронтенд разбит на ES-модули (`core/state/components/posts/subs/topics/
  nav/theme/app`) и отдельный `styles.css`.
- Появились тесты (`tests/`) и CI-шаг сборки образа.

## Запуск

```bash
python -m tg_spy --help
python -m tg_spy serve      # веб + API + MCP (uvicorn)
python -m tg_spy worker     # только планировщик + агент
python -m tg_spy migrate     # применить миграции БД
```

Переменные окружения (`HOST`, `PORT`, `DB_PATH`, `RSSHUB_BASE_URL`,
`MAX_DB_BYTES`, `AGENT_*`) сохранены для обратной совместимости.
